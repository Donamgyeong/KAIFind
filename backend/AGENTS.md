# 개발 환경 규칙

## 변경 사전 고지와 완료 보고

- 코드·설정·문서를 수정하기 전에 변경할 파일 또는 영역, 변경 내용과 목적을 사용자에게 알린다.
  작업 중 변경 범위가 늘어나면 추가 수정 전에 해당 내용을 알린다.
- 수정 완료 후에는 실제 변경한 파일 또는 영역과 변경 내용을 보고하고,
  수행한 테스트·검증 결과 및 남은 미검증 사항이 있다면 함께 명시한다.
- 사전 고지는 승인 요청과 구분한다. 사용자가 승인 절차를 별도로 요구하지 않았다면
  이미 요청받은 범위의 작업은 고지 후 진행한다.

## 구현 계획과 API 명세 확인

- 매 구현 계획을 수립하거나 변경할 때마다 `docs/api/README.md`와 관련 API 명세를 확인하고,
  계획이 명세의 엔드포인트, 요청·응답 모델, 인증·인가 및 동작 규칙에 어긋나지 않는지 검토한다.
- 명세와 불일치하는 부분이 있으면 구현 전에 해당 내용과 처리 방향을 계획에 명시한다.

## 코드 가독성과 줄바꿈

- import, 설정·상수, 클래스·함수 등 코드 섹션을 빈 줄로 구분한다.
- 함수 내부에서도 입력 검증, 인증·인가, 데이터 조회·처리, 저장, 응답 생성처럼
  역할이 바뀌는 지점에 빈 줄을 넣어 논리적 흐름을 드러낸다.
- 긴 함수 호출·조건식·딕셔너리는 여러 줄로 나누고 항목별 들여쓰기를 일정하게 유지한다.
  관련된 짧은 문장까지 무조건 한 줄씩 띄우거나 불필요한 구분 주석을 반복하지 않는다.
- 가독성만 정리하는 작업에서는 동작 변경을 섞지 않고 변경 전후 실행 구조와 관련 테스트로 검증한다.

## API 모델과 라우터 의존성 분류

- Pydantic 요청·응답·쿼리 모델은 `schema/`에 둔다. 쿼리 파라미터 모델도
  라우터에서 사용한다는 이유로 `router/`에 두지 않는다.
- 쿼리 모델을 별도 파일로 분리할 때는 `schema/<기능>_params.py`에 둔다.
  예: `schema/admin_params.py`, `schema/reference_params.py`.
- `Header`, `Cookie`, `Depends` 등 FastAPI의 HTTP 입력 추출·의존성 주입을
  담당하는 함수·클래스는 `router/`에 둔다. 예: `router/auth_params.py`의
  헤더·쿠키 의존성 dataclass. 파일명이나 dataclass 여부만으로 분류하지 않고
  실제 역할을 기준으로 판단한다.
- 한 파일에 Pydantic 모델과 FastAPI 의존성이 섞이면 역할별로 분리한다.
  파일 이동 시 import, 테스트, 관련 문서의 경로도 함께 갱신한다.

## 컨테이너와 의존성

- 실제 환경변수는 backend 상위 프로젝트 루트의 `.env` 한 곳에서 관리한다.
  새 환경변수도 해당 파일에 기존 값을 보존하며 추가하고, 비밀정보 없는 기본값·예시는
  같은 루트의 `example.env`에 함께 반영한다. backend 안에 별도 `.env`,
  `*.env.example`, `example.env` 등의 환경변수 파일을 만들지 않는다.
  컨테이너에 필요한 변수는 상위 `docker-compose.yaml`의 전달 설정도 함께 갱신한다.

- 기존 상위 `docker-compose.yaml`의 `backend`, `db`, `storage` 서비스를 사용한다.
  별도 Compose 프로젝트나 개발·테스트용 서비스 컨테이너를 새로 만들지 않는다.
- Python 실행, 테스트, 마이그레이션, 패키지 설치 및 의존성 검증은 반드시 실행 중인
  `backend` 컨테이너의 `/app`에서 수행한다. 호스트 Python·임시 가상환경은 사용하지 않는다.
- 소스는 `./backend:/app` 바인드 마운트로 공유된다. 소스 편집은 작업 공간에서 하고
  실행·검증은 `docker compose exec -T backend ...`로 한다.
- 라이브러리를 추가·업데이트하면 설치 전에 `requirements.txt`에 패키지와 버전을 반영한다.
  컨테이너에만 설치하고 끝내거나 `pip freeze`로 기존 목록을 통째로 덮어쓰지 않는다.
- 설치: `docker compose exec -T backend python -m pip install -r requirements.txt`.
  이미지도 같은 파일로 설치하므로 필요 시 `docker compose build backend`로 재현성을 확인한다.
- 테스트는 기존 `db` 서비스 안의 별도 `kaifind_test_*` 데이터베이스와 기존 `storage`의
  `kaifind-test-*` 임시 버킷을 사용한다. 개발 DB·개발 버킷을 TRUNCATE하거나 삭제하지 않는다.
- 기존 DB·MinIO 볼륨을 보존한다. `docker compose down -v`는 실행하지 않는다.
- 구체적인 명령은 `README.md` 및 `tests/README.md`를 참고한다.
