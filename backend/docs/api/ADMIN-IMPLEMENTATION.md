# 관리자 API 구현 현황

2026-11-03: 관리자 17개 엔드포인트와 MOD-01 회원 게시물 신고를 구현했다.
계약은 [관리자 명세](06-admin.md)를 따른다.

## 실행

Python 3.11 이상과 기존 Auth 설정·DB 연결 설정이 필요하다.
`alembic upgrade head`로 revision `20261103_0003`까지 적용한 뒤 서버를 실행한다.
건물 코드·언어별 카테고리 이름의 앞뒤 공백과 대소문자를 무시하는 고유 인덱스가 추가됐다.
기존 정규화 중복은 자동 병합하지 않으며 존재하면 마이그레이션이 실패한다.
이번 검증은 별도 테스트 DB에서 수행했으며 개발 DB에는 마이그레이션을 적용하지 않았다.

## 구현 구조

- `schema/admin.py`: 입력 검증, 페이지·응답 DTO, KST 시각 직렬화
- `router/admin_params.py`: 페이지·필터·시간 파라미터
- `library/protected_http.py`: 인증·현재 DB 역할·쓰기 CSRF·Origin·JSON 검증, 오류 계약, 요청 트랜잭션
- `service/admin.py`: 회원·기준정보·신고·분쟁·제한·통계·감사 조회
- `service/audit.py`: 감사 허용목록·값 형식 검증과 달력 기준 1년 보존 기한 계산

요청은 세션 행을 잠그고 만료·사용자·현재 역할을 검사한다. 성공 시 활동 시각과 유휴 만료를 갱신한다.
변경과 감사는 같은 트랜잭션에 속하고 응답 직렬화·커밋 실패도 성공 응답으로 반환하지 않는다.
민감 원문을 감사 metadata나 오류 로그에 복제하지 않는다.

모든 보호 요청은 공통 역할 advisory lock을 공유 모드로, 역할 변경은 배타 모드로 먼저 획득한다.
따라서 역할 회수는 진행 중인 보호 요청이 끝난 뒤 적용되고, 이후 요청은 갱신된 DB 역할을 검사한다.
역할 변경을 직렬화하여 마지막 ADMIN 동시 회수를 방지한다. 외부 SQL로 역할을 변경할 경우 이 규약을 따라야 한다.

신고 검토는 물품→신고, 분쟁 검토·수거 제한 변경은 수거자 users→분쟁 순서로 잠근다.
앞으로 구현할 수거 API도 동일 users 행을 잠근 뒤 제한을 검사해야 한다.
분쟁 검토는 원래 collection_id의 수거자를 기준으로 하며 수거를 자동 취소하지 않는다.

## 수거 제한 해제

제한 설정에는 인용 완료된 분쟁과 수거자 일치 검증이 필수다.
해제에는 disputeId를 생략할 수 있으며 제공한 경우에는 동일한 근거 검증을 수행한다.
근거가 삭제되면 FK SET NULL로 제한 자체는 유지한다. 해제를 위해 삭제된 근거를 복원하지 않는다.
제한 행이 없는 회원의 해제 요청은 false 상태 행을 생성하고 감사한다.
동일 상태·동일 근거 재요청은 기존 응답을 반환하고 변경 감사를 중복 생성하지 않는다.
명시적 해제까지 유지·해제 절차는 SRS 미정 사항을 보완한 설계 제안이다.

## 검증과 남은 연동

2026-11-03 전용 PostgreSQL 17 DB에서 전체 158개 테스트가 skip 없이 통과했다.
신규 revision의 downgrade→upgrade와 `alembic check`도 통과했다. 검증 후 임시 DB는 제거했다.

전용 `kaifind_test_*` PostgreSQL DB에서 마이그레이션 후 `python -m pytest tests -q`로 검증한다.
테스트는 HTTP 계약·개인정보 응답 제한·권한 즉시 반영·동시 회수/검토/생성·감사 실패 롤백과
근거 삭제 후 해제·숨김 포함 통계·시간 필터를 확인한다.

공개 습득물 조회·사진·매칭·수거 API는 아직 스텁이다. 해당 API 구현 시 hidden 재검사와
수거 제한 잠금 규약을 연결해야 한다. 지금은 숨김·제한 상태 저장과 admin 측 처리를 검증했다.
민감 자료 열람 감사·모든 비관리자 업무 이벤트 연동·보존 정리 배치·append-only 운영 DB 권한은 별도 작업이다.
