# 번역·키워드 기반 비동기 물품 매칭

작성일: 2026-11-07 (KST). 상태: DB 기반 구현, 분석·매칭 서비스 구현 전.

이 문서는 기존 다국어 임베딩 제안을 대체한다. DB 모델·마이그레이션은 구현했으며 번역 모델 실행·서비스·워커는 아직 구현하지 않았다. 물리 DB 구조와 트랜잭션 계약은 [DB 설계](translation-keyword-db-schema.md)를 따른다.

## 목표와 범위

한국어 공개 설명을 `Helsinki-NLP/opus-mt_tiny_kor-eng`로 영어로 번역하고, 정규화한 영어 키워드로 습득물과 분실 신고를 비교한다. 영어 입력은 번역을 건너뛴다. 습득물은 제목과 공개 설명, 분실 신고는 공개 설명을 입력으로 사용한다. 제목·설명은 경계를 보존해 처리한다.

비공개 식별 정보, 연락처, 보관 위치, 사진은 입력에 포함하지 않는다. 일반 검색과 키워드 구독은 기존 정책을 유지하며 이번 변경에 자동 편입하지 않는다. 임베딩·벡터 DB·pgvector는 도입하지 않는다.

## 실행 구조

```text
등록/수정 API
  → 원본 + 분석 요청 + outbox를 한 트랜잭션으로 저장
  → API 응답(등록 201, 분석 PENDING)

비동기 outbox 소비자
  → 분석 요청 확보
  → 전용 스레드: 번역 → 정규화 → 키워드 추출
  → 버전·lease 검증 → 분석 결과 + 재평가 작업 저장
  → 후보 재평가 → 후보 + 알림 outbox 저장
```

기존 backend 프로세스의 FastAPI 이벤트 루프에서 비동기 DB I/O와 작업 조율을 수행한다. `ThreadPoolExecutor(max_workers=1)`는 모델 로딩과 추론·키워드 추출만 담당한다. DB 세션이나 ORM 객체를 스레드에 전달하지 않고 입력 문자열과 설정만 전달한다. 작업 상태의 기준은 PostgreSQL이며 메모리 큐는 필수 구성 요소가 아니다.

초기 운영은 Uvicorn worker 1개를 전제로 한다. 프로세스마다 모델이 로딩되므로 worker를 늘리면 메모리 사용도 증가한다. 별도 Compose 서비스는 만들지 않는다. CPU 추론의 내부 스레드 수는 API 지연을 함께 측정해 제한한다.

## 모델 수명과 처리 한도

FastAPI lifespan에서 executor와 TranslationRuntime을 생성하고 전용 스레드에서 토크나이저·모델을 한 번 로딩해 워밍업한다. 로딩 성공 후 소비자를 시작한다. 로딩 실패 시 준비 완료로 표시하지 않는다. 종료 시 신규 작업 확보를 멈추고 실행 중 작업을 유예 시간 내 정리한다. 미완료 작업은 lease 만료 후 복구한다.

`AutoTokenizer`와 `AutoModelForSeq2SeqLM`을 직접 사용하고 `eval()` 및 `torch.inference_mode()`를 적용한다. 모델 revision, tokenizer revision, 라이브러리 버전, 생성 옵션, 입력 분할 규칙을 프로필에 고정한다. revision의 실제 commit과 의존성 버전은 컨테이너 호환성 검증 후 확정한다. 배포 전에 파일을 확보하고 런타임은 로컬 파일로 로딩한다.

모델 토큰 한도를 넘는 입력은 문장·토큰 단위로 분할한다. 조용히 잘라 버리지 않는다. 최대 조각 수·출력 길이를 정하고 실패는 분석 상태로 노출한다. executor에는 처리 가능한 작업만 제출하고 나머지는 DB에서 대기시킨다. 타임아웃은 실행 중 스레드를 강제 중단하지 않으므로 실제 추론 종료 전 후속 추론을 계속 쌓지 않는다.

## 키워드와 판정 규칙

초기 추출은 재현 가능한 규칙 기반으로 한다. Unicode·공백·대소문자 정규화, 불용어 제거, 단복수와 동의어 통합, 복합어 보존 규칙을 버전 관리한다. 브랜드·모델명·영숫자 식별자는 원문에서도 보조 추출한다. 부정 표현은 일반 긍정 키워드와 구분한다.

출력은 정렬·중복 제거한 canonical `text[]`와 종류별 JSON 속성이다. 예를 들어 `object:wallet`, `color:black`, `distinctive:cat sticker`처럼 종류를 포함한 토큰을 사용한다. 빈 키워드 결과는 정상 분석 결과지만 키워드 일치 근거가 될 수 없다.

```text
카테고리 동일
AND 발견일의 KST 날짜 >= 분실 시작일
AND (가능한 건물 일치 OR canonical 공통 키워드 존재)
```

분실 종료일을 발견일 상한으로 사용하지 않는다. 점수는 초기 후보 판정에 사용하지 않는다. 가중치 정렬은 추후 평가로 도입할 수 있다. 건물 근거는 텍스트 분석을 기다리지 않고 판정할 수 있다. 색상 등 흔한 단어만으로도 공통 키워드가 되는 현재 규칙의 정밀도는 실제 물품 데이터로 평가해야 하며, 임의로 임계치를 추가하지 않는다.

## 버전과 최신성

원본 `text_version`은 모델 입력 변경에만 증가하고 기존 `version`은 카테고리·날짜·상태를 포함한 판정 변경 검증에 사용한다. 분석 프로필과 매칭 정책은 불변 레코드다. 예전 버전의 분석이 늦게 끝나도 현재 결과를 덮어쓸 수 없다.

분석 완료 후 반대편의 준비된 분석과 비교한다. 양쪽 중 나중에 완료되는 작업이 다시 비교하므로 등록 순서에 따른 누락을 방지한다. 조건 변경은 번역을 재사용하고 재평가만 수행한다. 후보는 양쪽 버전이 일치하는 근거만 현재 근거로 노출한다. 전체 재평가 완료 전에는 과거 목록을 최신 목록으로 표시하지 않는다.

분석 상태와 매칭 상태를 별도로 응답한다. PENDING, PROCESSING, READY, FAILED를 사용하며 작업 내부의 SUPERSEDED는 현재 버전 작업 상태로 치환한다. 빈 후보와 처리 대기를 구분하고 실패를 일치 없음으로 표시하지 않는다.

수거 등 최신 후보가 필수인 쓰기는 관련 원본 집합의 잠금·재검증과 작업 완료 확인이 필요하다. 준비되지 않았다면 `MATCHING_PENDING`으로 전체 쓰기를 거부하고 재시도를 허용한다. 신고 하나의 READY만으로 전역 최신성을 판단하지 않는다. 구체적인 초기 직렬화 방식은 DB 설계의 최신성 절을 따른다.

## 실패·알림·보존

일시 오류는 지수 백오프와 jitter로 재시도하고 최대 시도 후 FAILED로 둔다. 수동 재시도는 같은 작업 ID를 재활성화하고 운영 감사에 기록한다. lease token이 다른 이전 작업자는 결과·실패·완료 상태를 쓰지 못한다.

후보의 최초 알림 기록과 기존 유일 키를 유지한다. 후보 저장과 알림 outbox 생성을 같은 트랜잭션으로 처리하고, 알림 생성·발송 직전에 숨김·삭제·신고 종료와 현재 근거를 재확인한다. 원문·번역문·키워드는 outbox와 일반 로그에 복제하지 않는다.

## 코드 배치와 구현 순서

| 영역 | 책임 |
| --- | --- |
| `main.py` | lifespan, 준비 상태, 종료 |
| `library/translation_runtime.py` | 모델 로딩, 동기 추론 |
| `library/text_keywords.py` | 정규화, 키워드 추출 |
| `service/text_analysis.py` | 분석 상태, 버전 검증, 결과 저장 |
| `service/matching.py` | 후보 검색·판정·저장 |
| `service/outbox_worker.py` | lease, 재시도, 소비 조율 |
| `schema/matching.py`, `schema/matching_params.py` | 응답과 쿼리 모델 |
| `model/`, `migrations/` | DB 구조와 이행 |

구현 순서는 DB 모델·마이그레이션 → 분석 런타임 → 작업 처리기 → 등록/수정 연동 → 매칭·조회 → 알림·수거 연동이다. 패키지는 먼저 requirements.txt에 고정 버전으로 기록하고 기존 backend 컨테이너 /app에서 설치·검증한다.

검증에는 번역 중 원본 수정, lease 만료 후 늦은 완료, 중복 처리, 양쪽 동시 등록, 분석 실패, 건물만 일치, 재평가 도중 조건 변경, 종료 직전 알림, 수거 직전 신규 물품을 포함한다. 번역 품질·RSS·처리량·대기시간은 실제 컨테이너에서 별도 측정한다.
