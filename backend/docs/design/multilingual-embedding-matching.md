# 다국어 임베딩 기반 물품 매칭 설계·구현 계획

> 2026-11-07: 이 문서는 이전 제안의 이력이다. 현재 기준은 [번역·키워드 매칭 구조](translation-keyword-matching.md)와 [DB 설계](translation-keyword-db-schema.md)다. 아래 임베딩·pgvector·별도 작업 프로세스 제안은 현재 구현 계획에 적용하지 않는다.

- 작성일: 2026-11-05 (KST)
- 상태: 구현 전 설계 제안. 아래 미정 사항은 구현 착수 전에 결정한다.
- 대상: 습득물·분실 신고 등록/수정, 임베딩 생성, 후보 갱신, 후보 조회 및 알림 연동
- 이 문서는 구현 완료를 의미하지 않는다. 기존 API·DB 명세와 다른 부분은 변경 제안이며, 정책 확정 시 관련 명세를 함께 갱신한다.

## 1. 배경과 목표

설명이 같은 의미여도 언어가 다르면 공통 키워드만으로는 매칭하기 어렵다. 다국어 임베딩으로 습득물과 분실 신고의 공개 설명을 벡터로 변환하고, 의미 유사도가 임계치를 충족하는 물품을 후보로 등록한다.

등록 API는 모델 응답을 기다리지 않는다. 원본과 작업 요청을 DB에 저장한 뒤 등록을 완료하고, 임베딩 생성과 후보 갱신은 비동기로 수행한다. 분실 신고의 임베딩도 저장하여 반복 매칭에 재사용한다.

이번 범위에는 이미지 임베딩, 검색 API의 의미 검색, 키워드 구독의 의미 매칭은 포함하지 않는다. 일반 검색·키워드 구독과 분실 신고 매칭은 별도 정책으로 유지한다.

## 3. 정책 결정 목록

| 항목 | 제안/기본안 | 확정 시점 |
| --- | --- | --- |
| 후보 조건 | 기존 건물 OR 조건을 유지하고 키워드를 의미 유사도로 교체 | 매칭 서비스 구현 전 |
| 임베딩 입력 | 양쪽 모두 공개 description만 사용 | 평가 세트 구성 시 |
| 습득물 제목 | 초기 입력에서 제외. 포함 여부는 비교 실험으로 결정 | 모델 평가 시 |
| 모델·리비전·차원 | 미정. 다국어 물품 설명 평가로 선정 | 벡터 컬럼·인덱스 확정 전 |
| 유사도 임계치 | 미정. 임의의 고정값을 채택하지 않음 | 품질 평가 후 |
| 비동기 실행 | 기존 backend 안의 별도 작업 프로세스, DB Outbox 사용 | 작업 처리기 구현 전 |
| 처리 지연 목표 | 등록→후보 반영 시간의 목표와 경보 기준 미정 | 성능 검증 전 |
| 수거 시 미완료 판정 | 아래 9절의 재검증/후속 처리 방식 중 선택 | 수거 연동 전 |
| 종료 신고 후보 | 기존 이력 조회를 유지하고 신규 후보·알림 생성 중단 | 상태 연동 구현 전 |

기존 후보 판정은 다음과 같다.

```text
카테고리 일치
AND 발견일(KST 날짜) >= 분실 시작일
AND (발견 건물이 가능한 건물에 포함 OR 공개 설명/제목에 공통 키워드)
```

호환성을 우선하는 제안은 다음과 같다.

```text
카테고리 일치
AND 발견일(KST 날짜) >= 분실 시작일
AND (건물 일치 OR 설명 유사도 >= 임계치)
```

이 규칙은 건물만 일치해도 후보를 만든다. 모든 후보에 임계치 충족이 필수라면 마지막 조건을 `설명 유사도 >= 임계치`로 바꾼다. 두 안은 서로 다른 제품 정책이므로 혼용하지 않는다. 기존 규칙대로 분실 종료일을 발견일 상한으로 추가하지 않는다.

후보 관계와 회원에게 노출 가능한 물품 상태는 구분한다. 숨김·삭제 물품은 조회와 알림에서 제외하고, 수거·만료·신고 종료 시 관계 보존 여부는 기존 명세와 일치시키며 신규 처리 가능 상태를 서비스에서 검사한다.

## 4. 임베딩 입력과 모델 계약

- 공개 description만 사용하며 비공개 식별 정보, 연락처, 보관 위치는 포함하지 않는다.
- 전처리는 공백·Unicode 등 최소한으로 적용하고, 실제 규칙을 버전으로 관리한다. 색상·브랜드·숫자처럼 구분에 필요한 정보를 제거하지 않는다.
- 입력 해시는 실제 모델 입력 문자열을 기준으로 생성한다. 해시는 임베딩 프로필과 함께 비교한다.
- 모델의 문서/검색어용 접두사나 인코딩 방식이 다르면 양쪽 역할을 프로필에 고정한다. 같은 모델명만으로 비교 가능하다고 가정하지 않는다.
- 최대 입력 길이, 초과 시 거부/절단 규칙, 정규화 여부를 명시한다. 실제 사용 언어에서 2,000자 설명을 처리할 수 있는지 검증한다.
- 모델 응답의 차원·유한한 수·0 벡터 여부를 검사한다. 잘못된 응답은 READY로 저장하지 않는다.
- 외부 API를 사용한다면 전송 데이터 범위, 보관 정책, 비용·호출 제한을 확인한다. 원문 설명과 API 키는 작업 로그에 기록하지 않는다.

공급자는 서비스 인터페이스 뒤에 둔다. 매칭 서비스는 특정 모델 SDK에 직접 의존하지 않고, 프로필과 역할·입력을 전달하여 벡터를 받는다. 같은 임베딩 프로필의 결과끼리만 비교한다.

## 5. DB 구조 제안

다음은 논리 구조이며 최종 DDL이 아니다. 모델 차원이 정해진 뒤 벡터 타입과 인덱스를 확정한다.

### 5.1 원본 테이블

found_items와 lost_reports에 `description_version bigint NOT NULL DEFAULT 1`을 추가한다. 실제 임베딩 입력이 바뀔 때만 증가시킨다. 기존 `version`은 카테고리·날짜·상태를 포함한 최신 판정 검증에 계속 사용한다.

보관 위치 등 설명과 무관한 변경으로 모델을 다시 호출하지 않는다. 설명을 변경한 트랜잭션에서 새 버전의 PENDING 행과 Outbox 이벤트도 함께 생성한다.

### 5.2 embedding_profiles

| 필드 | 의미 |
| --- | --- |
| id | 프로필 PK |
| provider, model_name, model_revision | 실행 모델과 고정 리비전 식별 |
| dimensions | 벡터 차원 |
| preprocessing_version, input_format_version | 입력 처리 규칙 |
| distance_metric, normalization | 비교 방식과 정규화 규칙 |
| created_at | 생성 시각 |

프로필은 생성 후 불변으로 취급한다. 활성 프로필은 명시적인 설정/정책 참조로 선택한다. 서로 다른 차원의 모델을 한 고정 차원 컬럼에 넣지 않는다. 모델 교체 시 별도 테이블·파티션 또는 차원별 컬럼 등 저장 전략을 마이그레이션에 포함한다.

### 5.3 found_item_embeddings / lost_report_embeddings

두 테이블은 같은 논리 구조를 가지며 각각 실제 원본 FK를 둔다. 다형적 entity_type/entity_id만으로 FK를 대체하지 않는다.

| 필드 | 의미 |
| --- | --- |
| id | 임베딩 행 PK |
| item_id 또는 report_id | 원본 FK, 영구 삭제 시 CASCADE |
| embedding_profile_id | 프로필 FK |
| description_version | 입력 원본 버전 |
| input_hash | 실제 입력 해시 |
| status | PENDING / PROCESSING / READY / FAILED |
| embedding | READY에서 필수, 그 전에는 NULL |
| created_at, completed_at | 요청·완료 시각 |
| last_error_code | 원문·비밀값을 포함하지 않는 오류 코드 |

제약은 `UNIQUE(원본 FK, embedding_profile_id, description_version)`와 상태/벡터 정합성 CHECK를 둔다. 최초 구현은 버전별 행을 사용하고, 이전 버전은 현재 검색에서 제외한다. 이전 벡터 보존 기간과 정리 작업은 운영 정책으로 정한다.

### 5.4 match_candidates 확장

- 기존 `UNIQUE(report_id, item_id)`, 최초 `matched_at`, 최초 알림 기록을 유지한다.
- `keyword_matched`를 `semantic_matched`로 전환하고 active 사유 CHECK를 새 정책에 맞게 수정한다.
- `semantic_score`, `embedding_profile_id`, `matching_policy_version`을 추가한다.
- 판정에 사용한 양쪽 임베딩 행 ID 또는 설명 버전과 양쪽 원본 version을 저장한다.
- 건물 일치만으로 생성된 후보는 의미 점수 미산출을 NULL로 표현한다. 미산출을 0점으로 저장하지 않는다.
- 임계치·판정식·입력 프로필은 불변의 matching policy 레코드 또는 버전 관리 설정으로 재현할 수 있어야 한다.

설명/조건 변경으로 판정이 오래되면 현재 의미 판정을 유효한 것으로 노출하지 않는다. 건물 조건만으로 여전히 유효한 후보는 정책에 따라 유지할 수 있다. 재평가 결과 불일치면 active=false로 만들고, 재일치하면 같은 행을 재활성화한다.

기존 keyword_matched=true를 semantic_matched=true로 그대로 복사하지 않는다. 기존 행은 새 정책으로 재평가하며, 이력과 알림 중복 방지 정보는 보존한다.

### 5.5 벡터 검색

기존 PostgreSQL에 pgvector를 설치하는 방안을 우선 검토한다. 별도 벡터 DB는 초기 범위에 넣지 않는다. 현재 일반 PostgreSQL 이미지에 확장 바이너리가 있는지는 미검증이며 SQL의 CREATE EXTENSION만으로 설치가 해결된다고 가정하지 않는다.

초기에는 카테고리·날짜 등으로 대상을 줄인 뒤 정확 비교를 수행한다. 코사인 사용 시 `similarity = 1 - cosine_distance`이며, 점수는 동일 물품일 확률이 아니다. 임계치 경계는 `>=`로 정의하고 테스트한다.

“임계치 이상인 모든 후보”가 요구사항이라면 임의의 top-k 제한을 후보 생성에 넣지 않는다. 배치로 나누어 전체 적격 집합을 처리한다. HNSW 등 근사 검색은 후보 누락과 필터 영향을 측정한 후 도입한다.

참고: [pgvector 공식 문서](https://github.com/pgvector/pgvector) — 정확/근사 검색, 거리 연산, 필터 및 인덱스 제약.

## 6. 비동기 처리와 트랜잭션

### 6.1 등록·설명 수정

1. 인증·입력·참조값을 검증한다.
2. 원본과 설명 버전을 저장한다.
3. 해당 버전·활성 프로필의 임베딩 PENDING 행과 생성 Outbox 이벤트를 같은 트랜잭션에 저장한다.
4. 커밋 후 등록은 201, 수정은 해당 API 계약에 맞게 응답한다. 모델 장애로 이미 저장된 등록을 실패로 바꾸지 않는다.

이벤트에는 원본 ID, 설명 버전, 프로필 ID 등 최소 식별자만 넣는다. 비공개 식별 정보와 원문 설명을 payload에 복제하지 않는다. 실행 시 원본 버전을 확인하고 최신 원문을 읽는다. 이미 다른 설명 버전이면 작업을 폐기하고 최신 작업 존재 여부를 보완한다.

### 6.2 작업 확보·임베딩 생성

1. 기존 Outbox의 attempts, next_attempt_at, lease_until을 활용하여 실행 가능한 작업을 짧은 트랜잭션으로 확보한다. 복수 처리기에서는 행 잠금과 SKIP LOCKED 등으로 중복 확보를 제한한다.
2. 원본 존재·처리 가능 상태·현재 버전을 검사하고 확보 트랜잭션을 종료한다.
3. DB 잠금 없이 모델을 호출한다. 시간 제한과 재시도 가능한 오류 분류를 적용한다.
4. 결과를 저장하는 트랜잭션에서 원본 버전과 작업 소유권을 다시 검사한다.
5. 유효하면 READY 저장, 재매칭 Outbox 생성, 생성 작업 완료 표시를 함께 커밋한다.

lease_until만으로 오래된 처리기를 차단하지 않는다. 확보 토큰 또는 증가하는 lease generation을 추가하여, 임대가 만료된 이전 처리기의 완료/실패 쓰기를 조건부 갱신으로 거부한다. 긴 호출에는 임대 갱신 또는 충분한 만료 시간과 호출 제한이 필요하다.

일시 장애는 지수 백오프와 jitter로 재시도하고 최대 횟수 후 FAILED로 둔다. 수동 재시도 경로와 경보 기준을 제공한다. 프로세스 종료 후 임대가 만료되면 다른 처리기가 재개할 수 있어야 한다.

기존 Outbox의 유일 키는 `(aggregate_id, aggregate_version, event_type)`이다. 동일 원본 버전에 여러 모델 프로필의 작업을 만들 때 충돌하지 않도록 임베딩 행 ID를 aggregate_id로 쓰는 등 이벤트 식별 방식을 먼저 확정한다. payload만 다르게 해서 같은 키를 재사용하지 않는다.

### 6.3 재매칭

1. 습득물 READY 시 기존 신고들을, 신고 READY 시 기존 습득물들을 검색한다.
2. 활성 프로필·현재 설명 버전의 READY 벡터만 비교한다.
3. 정책 조건과 유사도를 계산한다.
4. 후보 저장 시 양쪽 원본 version을 다시 확인한다. 바뀌었다면 오래된 결과를 반영하지 않고 최신 재평가를 예약한다.
5. 후보 upsert와 필요한 알림 Outbox 생성을 같은 트랜잭션에 수행한다.

후보 생성 후 조건을 잃은 기존 행도 재평가해야 한다. 새 검색 결과만 upsert하고 끝내지 않는다. 배치 완료 전에 검색 결과에 없다는 이유로 후보를 제거하지 않도록 실행 범위·완료 시점을 명시한다.

잠금은 기존 문서의 물품→신고 UUID 순서를 공통으로 적용한다. 교착/직렬화 실패는 트랜잭션 단위로 재시도한다. 외부 모델 호출과 대규모 탐색 동안 잠금을 유지하지 않는다.

## 7. 변경 이벤트별 동작

| 이벤트 | 처리 |
| --- | --- |
| 습득물/신고 등록 | 임베딩 생성 후 반대쪽 기존 데이터와 비교 |
| 설명 변경 | 이전 의미 판정 무효화, 새 임베딩 생성, 관련 후보 재평가 |
| 카테고리·날짜·건물 변경 | 기존 임베딩 재사용, 관련 후보 재평가 |
| 숨김·삭제·상태 변경 | 기존 명세에 맞게 노출·알림 차단 및 관계 처리 |
| 신고 종료 | 신규 후보·대기 알림 차단, 기존 이력 조회 정책 유지 |
| 임계치 변경 | 새 정책 버전으로 대상 후보 전체 재평가 |
| 모델 변경 | 새 프로필의 임베딩 배치 생성, 평가 후 활성 정책 전환 |

한쪽 벡터가 미완료이면 완료되는 쪽의 이벤트가 비교를 수행한다. 양쪽이 동시에 완료되거나 작업이 누락된 경우도 복구되도록 정기 정합성 작업을 둔다. 현재 버전의 벡터 부재, 만료된 임대, 미완료 재평가를 탐지하며 단순히 후보가 0개라는 이유로 무한 재실행하지 않는다.

## 8. API·알림 계약

- matchingStatus: PENDING / PROCESSING / READY / FAILED를 제공하는 안을 기본으로 한다.
- READY는 임베딩 생성뿐 아니라 해당 정책·버전의 후보 갱신까지 완료되었음을 뜻한다.
- 부분 결과가 있으면 처리 중임을 함께 반환한다. 결과 0개와 미처리를 구분한다.
- 양방향 매칭 진행 중에도 완료 상태가 오래 남지 않도록 재평가 요청 버전과 완료 버전 또는 동등한 진행 기록을 둔다. 이 기록이 참조하는 평가 범위와 정책 버전을 명시한다.
- 후보 목록 GET은 작업 생성이나 알림 발송을 하지 않는다.
- matchedBy의 KEYWORD를 SEMANTIC으로 바꾸는 API 변경을 명세·클라이언트에 반영한다. 건물 근거를 유지하는 정책이면 BUILDING도 유지한다.
- 기본 정렬은 기존 matchedAt 내림차순과 candidateId 내림차순을 유지한다. 유사도 정렬은 별도 제품 결정 없이 추가하지 않는다.
- 소유자/관리자 권한, 숨김·삭제·민감 물품 노출 제한은 기존 계약을 유지한다.
- 알림 생성과 발송 시 신고 상태·물품 노출 상태·수신 설정을 재검사한다. 이벤트 재처리와 후보 재활성화로 최초 알림이 중복되지 않도록 DB 유일 키와 기존 알림 기록을 사용한다.

## 9. 수거 시 신고 자동 종료

기존 설계는 수거자가 해당 물품을 후보로 가진 OPEN 신고들을 자동 종료한다. 비동기 전환 후 오래된 후보나 아직 생성되지 않은 후보를 그대로 기준으로 삼으면 오종료·누락이 발생할 수 있다.

구현 전 다음 중 하나를 명시적으로 선택한다.

1. 수거 전 필요한 최신 벡터가 준비된 경우 짧은 트랜잭션에서 현재 조건과 점수를 다시 판정한다. 벡터가 없을 때의 재시도 응답·수거 허용 정책을 별도로 정한다.
2. 수거 자체를 기록한 뒤 후속 작업으로 신고 종료를 처리한다. 수거 시점의 설명 버전·조건을 식별할 수 있는 스냅샷을 보존하고 종료가 지연됨을 API 계약에 반영한다.

모델 호출을 수거 DB 트랜잭션 안에 넣지 않는다. 판정 시점·상태를 정의하지 않은 채 “최신 후보만 사용”이라고만 구현하지 않는다. 후속 작업은 타인 신고를 종료하지 않고, 수거 취소가 종료 신고나 삭제된 비공개 정보를 복원하지 않는 기존 정책을 지킨다.

## 10. 모델·임계치 평가

실제 물품 설명에 가까운 정답 쌍과 비정답 쌍을 준비하고, 임계치 조정용 데이터와 최종 평가 데이터를 분리한다.

- 언어가 다른 동일 의미 설명, 한국어/영어 및 실제 서비스 대상 언어
- 짧은 설명, 혼합 언어, 오타, 생략된 특징
- 같은 물품 종류지만 색상·브랜드·모델·특징이 다른 어려운 비정답
- 흔한 표현이 겹치는 서로 다른 물품

후보 누락률·오탐률을 언어 조합별로 측정한다. 건물 OR 정책이면 의미 매칭 단독 성능과 최종 후보 정책 성능을 구분한다. 처리 시간, 등록→후보 반영 지연, 재시도율, 비용도 측정한다.

모델·임계치는 평가 후 확정한다. 모델이 바뀌면 점수 분포도 달라지므로 이전 임계치를 그대로 재사용하지 않는다. 외부 모델의 리비전을 고정할 수 없다면 동작 변경 감지와 재평가 정책을 마련한다.

활성화 전 기존 데이터에 새 프로필 임베딩을 배치 생성한다. 일괄 처리에는 재개 위치·배치 크기·속도 제한을 둔다. 새 정책 결과를 먼저 비교하고 활성 프로필/정책을 전환한다. 전환 과정에서 기존 후보의 최초 시각과 알림 기록을 잃지 않는다. 롤백 시 되돌릴 프로필·정책과 후보 재평가 절차를 준비한다.

로컬/통합 테스트는 고정 벡터 공급자로 재현 가능하게 작성하고 실제 모델 품질 평가는 별도로 수행한다. 의미 없는 임의 벡터 테스트를 다국어 품질 검증으로 보고하지 않는다.

Python 실행·테스트·마이그레이션·설치는 실행 중인 기존 backend 컨테이너의 /app에서만 수행한다.

```sh
docker compose exec -T backend python -m scripts.test_backend
```

테스트는 기존 db 서비스의 별도 kaifind_test_* DB와 필요한 경우 기존 storage의 kaifind-test-* 버킷을 사용한다. 개발 DB/버킷을 초기화하지 않는다. 새 서비스 컨테이너를 만들거나 기존 볼륨을 삭제하지 않는다. 라이브러리는 requirements.txt에 버전을 먼저 반영한다. db 이미지 변경 시 PostgreSQL 메이저 버전과 데이터 디렉터리 호환성을 확인하고 기존 볼륨을 보존한다.

## 13. 운영 점검과 현재 미검증 사항

관측 항목은 미처리 작업 수·가장 오래된 작업의 대기 시간, 재시도/실패 수, 임베딩 지연, 후보 반영 지연, 모델 비용, READY 벡터 누락 수다. 실패 작업 재실행과 정합성 복구 명령의 사용법을 운영 문서에 추가한다.

현재는 설계 문서만 작성한 상태다. 모델·임계치, pgvector 설치 가능 여부, 실제 모델 품질·비용·처리량, 작업 프로세스의 운영 방식, 수거 연동 정책은 아직 검증/확정되지 않았다. 이 문서 작성으로 코드·DB·실행 환경이 변경되지는 않는다.
