# 분실 신고 API 구현

2026-11-13. [API 목차](../api/README.md), [분실 신고 계약](../api/03-lost-reports-matching.md),
[분석 연결 규약](translation-keyword-implementation-plan.md), [일일 만료](daily-expiry.md)를 기준으로 한다.

## 범위

LOST-01~06을 기존 LostReport·건물 연결·비공개 정보 테이블에 연결했다.
DB 마이그레이션, 패키지, 환경변수 추가는 없다. MATCH-01의 읽기 전용 계약을 유지한다.
관리자는 타인의 상세만 조회할 수 있으며 목록은 본인 신고만, 쓰기는 본인만 허용한다.
존재하지 않는 신고와 권한 없는 신고는 같은 LOST_REPORT_NOT_FOUND 응답이다.

## 저장과 작업 연결

ProtectedRoute가 인증·CSRF·Origin·입력 검사와 트랜잭션을 소유한다.
신규·변경 원본, 건물, 비공개 정보, 분석 outbox, 재평가 generation, 상태 감사를 함께 커밋한다.
공개 설명 변경은 DB text_version 트리거와 request_lost_report_analysis로 연결한다.
그 외 수정과 연장은 번역을 재사용하고 request_report_reevaluation을 호출한다.
비공개 정보만 바꿔도 신고 version 변경을 반영해 재평가한다. 비공개 원문은 분석·이벤트·감사에 넣지 않는다.
PUT은 전체 교체이며 기존 비활성 참조는 유지할 수 있지만 새 선택은 활성 참조여야 한다.
날짜 검사는 요청 clock의 KST 날짜를 사용하며 숫자 타임스탬프·시각 문자열은 날짜로 받지 않는다.

잠금 순서는 인증 공통 잠금 → 정렬된 카테고리 advisory 잠금 → 신고 행이다.
카테고리 변경은 이전·새 카테고리를 한 번에 잠그고 행을 다시 읽어 스냅샷을 검증한다.
불일치는 CONCURRENT_MODIFICATION으로 전체 롤백한다.
목록 만료 정리는 대상 카테고리를 모두 먼저 잠그고 신고 UUID 순으로 처리한다.

## 만료와 해결

등록 유효기간은 30일, 연장은 max(expiresAt, now)+30일이다. 별도 연장 횟수 제한은 없다.
상세·목록은 접근한 대상의 만료 상태를 실제 CLOSED로 저장한다. 목록은 상태 필터 전에
본인의 기한 경과 OPEN 신고를 정리한다. MATCH-01은 기존대로 읽기 전용 상태 투영을 사용한다.
수정·연장은 만료 정리 후 LOST_REPORT_NOT_OPEN 409를 정상 Response로 반환하여
CLOSED·개인정보 삭제·SYSTEM 감사가 오류 응답과 함께 커밋되게 한다.
다른 예외는 기존 공통 처리에 따라 롤백되며, 일반 오류를 커밋하는 공통 예외 규칙은 추가하지 않았다.

최초 종료 시 closedAt=요청 시각, purgeAfter=그 시각의 1년 후를 기록한다.
상태 변경 DB 트리거가 비공개 정보 삭제와 대기 이메일 취소를 처리한다.
분석·매칭 워커와 발송자는 상태를 재검사하여 종료 후 작업·신규 알림을 억제한다.
CLOSED→RESOLVED는 최초 종료·보존 기한을 유지하며 RESOLVED 재요청은 변경·감사 없이 200이다.
기존 후보와 완료 분석 이력은 유지한다. 1년 후 물리 삭제 작업은 별도 범위다.

## 응답과 검증

상세·요약 모델을 분리해 목록에 비공개 필드가 나타나지 않게 한다.
건물 연결은 목록에서 일괄 조회하며 처리 상태는 기존 matching_progress를 재사용한다.
처리 상태 집계는 현재 신고마다 실행하므로 최대 페이지의 대량 후보 데이터 성능 검증은 후속 과제다.
HTTP 등록→분석 워커→매칭 워커→후보와 처리 상태 조회를 mock 및 opt-in 실제 번역 모델로 검사한다.
권한·입력·종료·비활성 참조·원자적 롤백·동시 연장/해결은 전용 PostgreSQL DB에서 검증한다.
실행 방법과 실제 결과는 [테스트 안내](../../tests/README.md)를 참고한다.
